📝 交易与脚本

当你"发一笔比特币"，背后到底发生了什么？UTXO 模型、Script 脚本、从 P2PKH 到 Taproot 的地址类型演进——一页讲透。

💡 核心直觉

比特币没有"余额"概念。你的比特币不是放在一个账户里，而是以一堆"未花掉的零钱"形式散落在链上。交易不是"从A转给B"，而是"撕掉几张旧票据，签发几张新票据"。

每笔交易的执行，都由一段微小程序（Script）控制——谁能用这些币，由代码说了算。

一、UTXO 模型：比特币的"钞票"体系

1.1 什么是 UTXO？

UTXO = Unspent Transaction Output（未花费交易输出）。

想象一下：你钱包里有不同面值的钞票——一张 100 元、一张 50 元、两张 20 元。你的"余额"是这些钞票的总和，而不是账户里一个数字。

比特币完全一样：

  • 每一笔交易的输出（output）就是一张"钞票"
  • 这张"钞票"尚未被花掉 → 它就是 UTXO
  • 一旦被花掉 → 从 UTXO 名单中移除
  • 你的"比特币余额" = 所有你控制的 UTXO 的面值之和

1.2 UTXO 的核心特性

🔗

线性消耗

一旦被花掉就消失，不能部分花费。必须花掉整个 UTXO。

🔍

全局可见

所有 UTXO 都在链上，任何人都可以验证"这张钞票是否还在"。

🔑

脚本锁定

每个 UTXO 都被一段 Script 锁定，只有满足条件才能解锁花费。

📊

状态累积

全节点维护 UTXO 集（当前所有未花输出），是比特币状态的"快照"。

💎 为什么用 UTXO 不用账户模型？

以太坊用"账户余额"模型（类似银行），比特币坚持 UTXO。原因：

  • 并发性：多笔交易可并行验证，互不冲突（每笔交易只花自己的 UTXO）
  • 隐私性：没有"账户"，地址可每次换新，追踪更难
  • 简洁性：不存在"余额篡改"——要么 UTXO 存在且未花，要么不存在
  • 可验证：全节点只需维护 UTXO 集就能验证所有交易，无需知道历史

二、交易结构：扒开一笔交易的"内脏"

每一笔比特币交易，本质上是一个数据结构。先看宏观骨架：

📋 比特币交易数据结构
Version（版本号）
0x01000000
4 字节，标识交易格式版本。SegWit 交易通常为 1 (0x0001)。
Marker + Flag
0x00 0x01
SegWit 标记（非 SegWit 无此字段）。Marker=0x00, Flag=0x01。
Input Count（输入数量）
0x02
CompactSize 编码，表示后面有多少个输入。
Inputs（输入列表）
每个输入包含：
Previous TxID (32字节)
Output Index (4字节，vout)
ScriptSig / ScriptWitness (变长)
Sequence (4字节)
Output Count（输出数量）
0x02
CompactSize 编码，表示后面有多少个输出。
Outputs（输出列表）
每个输出包含：
Amount (8字节，以 satoshi 为单位)
ScriptPubKey (变长，锁定脚本)
Witness Data
SegWit 专属。每个输入对应一个见证数据栈。
Locktime（锁定时间）
0x00000000
4 字节。指定交易何时生效（区块高度或时间戳）。

2.1 输入结构详解

🔍 输入 = 指向"旧钞票"的引用

每笔交易输入不是拿"币"本身，而是引用历史上某个交易的一个输出（UTXO）。

包含两个关键信息：

  • Outpoint = txid:vout —— 你要"撕掉的旧钞票"在哪
  • 解锁证明 —— 证明你有权花掉它（私钥签名或满足脚本条件）

2.2 输出结构详解

📤 输出 = 发新钞票"

每笔输出创造一张新钞票，包含：

  • Amount：面值，以 satoshi 为单位（1 BTC = 100,000,000 sat）
  • ScriptPubKey：锁定条件（下一个持票人必须满足什么条件才能花）

输出一旦创建，就成为 UTXO，直到被新交易的输入引用并花费。

2.3 交易 ID（TXID）

每笔交易的哈希值就是它的唯一标识——txid。

但这里有个重要的细节：

SegWit 的双重 ID

TXID = 不含 witness 部分的交易哈希（SegWit 中不受影响）

WTXID = 含 witness 部分的交易哈希

这就是 SegWit 实现"见证数据隔离"的关键——第三层不参与 TXID 计算，所以任何人都可以在不改变 TXID 的前提下剪切 witness 数据（未来节点可选择性忽略历史见证数据）。

三、Script 脚本：比特币的"可编程锁"

3.1 栈式执行语言

比特币 Script 是一种精巧的基于栈的脚本语言，设计极度克制——

📚

非图灵完备

没有循环/递归，保证每个脚本都终止运行——避免"停机问题"。

🧮

栈式运算

数据压入栈，操作码从栈顶取数据运算，结果再压回栈。

🔍

签收验证

脚本执行后，栈顶为 true → 验证通过。否则交易无效。

🔒

隔离安全性

无跳转指令，无法构造死循环，恶意脚本只能在有限范围内捣乱。

3.2 常用操作码

操作码 值 描述
OP_DUP 0x76 复制栈顶元素
OP_HASH160 0xA9 栈顶元素先 SHA-256 再 RIPEMD-160
OP_EQUALVERIFY 0x88 检查栈顶两个元素是否相等，不等则脚本失败
OP_CHECKSIG 0xAC 验证签名：公钥 + 签名 → true/false
OP_CHECKMULTISIG 0xAE 验证 m-of-n 多重签名
OP_RETURN 0x6A 标记输出不可花费（用于数据嵌入）
OP_CHECKSIGADD 0xBA Taproot 新增，累加签名计数（替代 CHECKMULTISIG）

3.3 P2PKH 脚本示例：经典"转账"

最常见的一对一转账模式——Pay-to-Public-Key-Hash（支付到公钥哈希）。

🧪 P2PKH 脚本执行过程模拟（简化）

锁定脚本（ScriptPubKey）： OP_DUP OP_HASH160 <pubKeyHash> OP_EQUALVERIFY OP_CHECKSIG
解锁脚本（ScriptSig）： <sig> <pubKey>

▼ 拼接脚本 <sig> <pubKey> OP_DUP OP_HASH160 <hash> OP_EQUALVERIFY OP_CHECKSIG []
① <sig> 压入签名 [sig]
② <pubKey> 压入公钥 [sig, pubKey]
③ OP_DUP 复制栈顶（公钥） [sig, pubKey, pubKey]
④ OP_HASH160 对 pubKey 哈希 [sig, pubKey, hash(pubKey)]
⑤ <pubKeyHash> 压入脚本中的哈希 [sig, pubKey, hash(pubKey), expectedHash]
⑥ OP_EQUALVERIFY 比较两个哈希 → 相同则删除，继续 [sig, pubKey]
⑦ OP_CHECKSIG 验证签名：pubKey 是否签署了这笔交易？ ✅ true

💎 脚本设计哲学："先签名后锁定"

你可能注意到：签名在解锁脚本中，但签名验证的却是整笔交易。这造成了一个"先有鸡还是先有蛋"的悖论——签名要验证交易，但交易还没构建完。

比特币的解决方案是：在构造交易时，解锁脚本留空（或填入占位数据），计算签名后再填入。这个巧妙设计使得签名本身不可篡改——改了签名数据，签名验不过；改了输出/金额，签名也验不过。

四、地址类型演进：从 1 开头到 bc1

地址实际上是ScriptPubKey 的一种编码表示。地址类型的演进，本质上是 Script 脚本的演进。

🔴 P2PKH Legacy

📈 地址演进趋势

从 P2PKH 到 P2TR，清晰看到比特币脚本哲学的进化：从显式到隐式，从确定性到隐私性。

P2PKH 告诉你"这后面是一个公钥"，P2TR 对所有人说"不知道，可能是一个公钥，也可能是一个复杂的脚本树"——而矿工和验证节点也不知道你的真实意图。

五、SegWit：见证数据隔离的革命

5.1 为什么需要 SegWit？

2017 年比特币面临两个核心问题：

  • 区块容量：1MB 限制了每秒约 7 笔交易，扩容呼声震天
  • 交易延展性：签名在 TXID 计算范围内，第三方可在广播前修改签名，改变 TXID 却不影响交易有效性——导致闪电网络无法安全实现

SegWit（隔离见证）一石二鸟地解决了这两个问题。

5.2 SegWit 做了什么？

⚡ SegWit 的核心改动
改动 1
签名（见证数据）从输入中移出
放入新的 Witness 字段，不参与 TXID 计算 → 第三方无法更改 TXID
改动 2
旧 1MB 限制 → 4M 重量单位
Witness 数据按 1x 权重计算，非见证数据按 4x → 实际区块可达 ~4MB
改动 3
新地址格式（Bech32）
bc1 开头，更短的二维码，内置校验（检测输入错误）

5.3 重量单位（Weight Units）

SegWit 引入了 WU（重量单位）的概念，替代了旧的"字节"限制：

⚖️ 重量计算规则
  • 非见证数据（版本、输入、输出、locktime）× 4
  • 见证数据（witness） × 1
  • 总和 ≤ 4,000,000 WU（≈ 4MB）
  • 旧区块 1,000,000 字节 = 4,000,000 WU（完全向后兼容）

5.4 SegWit 的实际收益

交易类型 旧大小 (bytes) SegWit (vBytes) 节省
P2PKH (单签) 192 ~122 (P2WPKH) 36%
P2SH 2-of-3 多签 ~366 ~177 (P2WSH) 52%
P2TR 单签 — ~127 比 P2WPKH 略高但功能更强

vBytes = 虚拟字节。见证了数据 1/4 的实际空间（4 WU = 1 vByte）。

六、多视角重新解释

🔄 多视角 · 同一笔交易，六种身份
⚙️ 协议开发者
"脚本语言的设计是比特币最精妙的权衡——提供足够的表达力以满足基本验证需求，但严格限制以防图灵完备带来的安全灾难。"
  • 安全优先：无循环/递归，保证脚本终止；早期禁用 OP_CAT/OP_MUL 等操作码，以防 DOS 攻击
  • 模块化升级：P2SH 允许"不知道具体条件也能接收"，SegWit 协议升级不改变 TXID，Taproot 通过 MAST 树支持条件分支
  • 向后兼容：SegWit 以软分叉实现——老节点看到 Witness 标记认为"任何 valid 的签名都可以"
  • 当前焦点：OP_CAT、CTV(BIP-119)、CSFS(BIP-348) 等新操作码是否应重新激活？安全性审查仍在进行
🔍 链上分析师
"每一枚 satoshi 都可以从创世块追踪到今天。UTXO 模型让资金流谱系完全透明——追踪比洗钱更困难。"
  • UTXO 追踪：通过"共同花费"启发式——同一交易中的多个输入很可能属于同一个实体
  • 地址聚类：找零地址通常符合特定模式（新生成的地址、金额不等于任意输入），可归属到原始地址
  • Coinjoin 检测：均衡金额输出 + 多参与者输入 = 大概率 CoinJoin 混币
  • 收发单分析：大额 UTXO 拆分、交易所热钱包归集、矿池支付模式均可通过 UTXO 图谱可视化
  • 隐私挑战：Taproot 使交易"看起来都一样"，链上分析正在从模式识别转向机器学习
🕵️ 隐私研究者
"Taproot 是比特币隐私的范式转移——不是通过隐藏数据，而是通过隐藏复杂性，让所有交易看起来一模一样。"
  • Homogeneity（同质化）：P2TR 迫使传统单签、多签、时间锁交易对外表现相同——外界完全无法区分
  • MAST（Merkle Abstricted Syntax Tree）：执行时只暴露执行的路径，隐藏所有未使用的分支——多签条件对外界不可见
  • CoinJoin 的新可能：Taproot 让混币交易更难识别，因为所有参与者输出都是"看起来一样"的 P2TR
  • 支付聚合：多个输入可以聚合为单一 Schnorr 签名（通过 MuSig 协议），链路分析更难关联
  • 挑战：链上数据分析师转向"金额模式分析"等新方法，隐私工程和去匿名化技术仍在军备竞赛
👛 钱包开发者
"最令用户困惑的设计：为什么我收到 0.01 BTC，却不能用 0.01 BTC 支付 0.009 BTC？UTXO 碎片的心理成本远超预期。"
  • UTXO 选择算法：核心问题——从钱包的 UTXO 集合中选择哪些来满足支付金额，同时最小化费用
  • 常见策略：
    • Best-fit 最适匹配：选略大于支付金额的 UTXO（产生最小找零）
    • Knapsack 背包算法：寻找最佳 UTXO 组合，最小化总金额与支付目标的差距（减少找零）
    • Single-random-draw：随机挑选 UTXO，增加隐私性（更难以关联）
  • 找零地址管理：永远使用新地址接收找零，不与支付输入地址重复 → 链上分析更难追踪
  • UTXO 合并：低费率时合并小额 UTXO（dust），避免高费率时"花不起"（UTXO 面值小于手续费）
  • 隐私-效率权衡：合并 UTXO 提高效率但暴露了你控制这些 UTXO，需权衡
💰 经济学者
"手续费不是 Bug，而是比特币网络安全的经济学基石——它驱动资金从低价值交易流向高价值交易。"
  • 手续费 = 区块空间的竞价拍卖：区块空间有限（~4MWU/10min），矿工优先打包出价最高的交易
  • sat/vB：费率单位，每虚拟字节的聪数。高 sat/vB → 优先入块
  • RBF（Replace-by-Fee）：交易尚未确认，用更高手续费替换原交易——竞价上车
  • CPFP（Child-Pays-For-Parent）：你收到一个低费率交易 A（未确认），你创建依赖 A 的交易 B 并付高费——矿工同时打包 A 和 B
  • 手续费市场的行为经济学：网络拥堵时，用户恐慌出价导致费率飙升（2023 年 Ordinals 铭文拥堵期间，平均费率突破 300 sat/vB）
  • 手续费 vs 区块奖励：随区块奖励逐渐减半（约 2140 年归零），手续费将完全替代区块奖励成为矿工收入来源，届时比特币的安全预算足够吗？
📜 历史学家
"2017 年 SegWit 之争不仅是技术分歧——它暴露出比特币没有治理中心的无序与韧性。"
  • 2010 年脚本漏洞：OP_LSHIFT/OP_RSHIFT 操作码存在整数溢出漏洞（CVE-2010-5139），攻击者可创建无限量比特币。中本聪紧急发布 0.3.17 版本禁用问题操作码
  • 2012 年 P2SH：在 Bitcoin Core 0.6.0 中引入，BIP-16。支持支付到脚本哈希，允许发送方无需知道接收方脚本细节。软分叉实施
  • 2014-2017 区块大小战争：1MB 瓶颈让社区分裂——大区块派主张直接扩容（Bitcoin XT，Bitcoin Classic，Bitcoin Unlimited）；Core 开发者主张 SegWit 软分叉
  • 2017 年 8 月 UASF（用户激活软分叉）：用户和节点运营者通过 BIP-148 强制激活 SegWit，绕过矿工阻挠。这是"用户主权"的经典案例
  • 2017 年 8 月 1 日：BCH 分叉，拒绝 SegWit，走大区块路线
  • 2021 年 Taproot：BIP-340/341/342，Schnorr 签名 + MAST + Tapscript。自 SegWit 以来最大的协议升级，几乎无争议通过
  • 2023-2026 新一波争论：铭文(Ordinals/Runes)利用 SegWit 的数据空间承载数据；BIP-420 OP_CAT 重新讨论；BIP-110 限制铭文——历史再次重演：创新性应用 vs 原始设计意图的张力

八、大白话总结

💡 把这些复杂的放在日常场景中

UTXO = 一张张"未花掉的钞票"

  • 你的比特币不是"账户余额"，而是一堆不同面值的钞票
  • 买杯咖啡 0.003 BTC？你递过去一张 0.01 BTC 的钞票，对方找你 0.00697 BTC（扣掉 30 聪小费）
  • 这 0.01 BTC 的钞票被"销毁"，换来一张 0.003 BTC + 0.00697 BTC 的新钞票

交易 = 撕掉旧钞票，签发新钞票

  • 输入 = 你要撕掉哪些旧钞票 | 输出 = 签发哪些新钞票
  • 差额 = 小费给收银员（矿工）
  • 旧钞被撕毁 = UTXO 从"未花费"列表中移除
  • 新钞签发 = 新 UTXO 进入列表

Script = 钞票上的"解锁谜题"

  • 每张钞票上都写着一道谜题："只有能提供正确签名且公钥哈希符合以下条件的人才能花"
  • 你要花它时，需提供谜底（签名+公钥）
  • 验证节点就是"裁判"——按规则检查谜底是否正确

手续费 = 给小费（给矿工）

  • 你的钞票总面值 - 签发的新钞总面值 = 小费（手续费）
  • 小费给得越多，收银员（矿工）越积极帮你处理
  • 网络拥堵时大家都在加小费 → 手续费飙升
📦 地址类型的"演化故事"

想象比特币是一个菜市场：

  • P2PKH（1开头） = 每个摊位前都挂着"此摊位需要：出示身份证 + 签名确认"的招牌。所有人都能看懂。
  • P2SH（3开头） = 招牌上只写了一个编号"请到 XXX 仓库查看具体验证规则"。你不知道后面是多签还是什么，只要满足就行。
  • P2WPKH（bc1q开头） = 身份证和签名不需要在招牌上展示，放进"额外单"里。招牌更短更干净，而且别人改不了你的签名。
  • P2TR（bc1p开头） = 招牌上只有一句话"负责人：张三"。但张三背后可能有一个复杂的律师团队、三个合伙人、或者一个遗嘱执行人——但外人完全看不出。

本章核心要点

1️⃣

比特币没有"余额"——只有一堆 UTXO（未花费交易输出），你的"余额"是这些 UTXO 面值之和

2️⃣

交易 = 输入 + 输出——输入引用旧 UTXO（要花掉的钞票），输出创建新 UTXO（新钞票）

3️⃣

Script 脚本是比特币的可编程锁——每笔输出都被一段脚本锁定，只有满足条件才能花费

4️⃣

SegWit移除了签名对 TXID 的影响并引入重量单位概念——实际提升了区块容量并修复了交易延展性

5️⃣

Taproot让所有交易看起来一样——多签/时间锁对外界不可见，这是比特币隐私的范式转移

6️⃣

手续费 = 区块空间拍卖——矿工优先收取高费率交易，RBF/CPFP 是两种"加价插队"方式
