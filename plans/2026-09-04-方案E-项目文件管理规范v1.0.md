- `v2` = v2-B-01 系列（教育风·暖色主导）

- 封面模板：`cover_template_v{N}.py`（v1→v5 已迭代 5 代，**当前在用 v5**）
- L1 检验：`cover-lint.py`（同步演进，无版本号）
- 文章镜像：`mirror-articles.mjs`（同步演进，无版本号）

### 5.3 文章版本
- 用 `站N-` 前缀做版本号（站号=版本）
- 同站重写 → 旧版进 `archive/`，新版在原位
- **不**在文件名加 `-v2`、`-新`、`-改` 后缀

## 六、旧文件归档策略

### 6.1 触发条件（满足任一即归档）
1. 新版本落地（同名文件被新版本覆盖前）
2. 文件超过 6 个月未被访问
3. 用户明确说"归档"或"作废"

### 6.2 归档位置
- 同类型目录下 `archive/` 子目录
- 跨类型归档：`项目根/archive/`

### 6.3 归档命名
- 保留原名 + 加日期后缀（**不**用 `-old` / `-v1` / `-已废` 风格前缀）
- 例：`cover_template_v4.py` → `archive/cover_template_v4-2026-09-04.py`

### 6.4 纪律（个人目录高风险）
- **不删**只移（mv 不 rm）
- 全部先备份（cp）→ 验证 → commit → 推
- 单文件 mv（绕开 macOS 多文件 mv bug）

## 十一、变更风险与回滚

### 风险点
1. `assets/cover/` 合并可能影响 git 跟踪（文件重命名）
2. `content-source/` 是 gitignored，移动不影响 git 状态
3. `archive/` 是 gitignored，移动不影响 git 状态

### 回滚策略
- 所有 `mv` 操作的源路径都在 commit message 列出
- 任何归档/合并前先 git status 看清楚
- 出问题立即 `git reset --hard HEAD^`（仅对 git 跟踪的文件）
- gitignored 目录出问题 → `mv` 反向操作

1. **每次任务开始前**：先 Read `README.md` 项目地图，确认目标路径
2. **每次产出后**：立刻 commit + 立刻更新 README 索引（如有新增常驻文件）
3. **每周一次**：检查 `archive/` 是否需要进一步压缩
4. **每月一次**：检查 `gitignored` 目录（samples/content-source/tools/dev/out）是否需要清理
5. **重大重构前**：先 `plans/` 写方案 → 用户拍板 → 执行
